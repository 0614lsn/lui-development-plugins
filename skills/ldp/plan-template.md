# Plan 模板（LDP 阶段 1）

按本模板写 `YYYY-MM-DD-<topic>-plan.md`，放目标仓 `docs/development/`，commit 到 feature 分支后直接将 plan 本身提交人工审核。plan 批准是本需求唯一的常规人工闸门：写 plan 前先把待澄清问题批量问完并把裁决写进「预裁决记录」，把原需中途确认的动作写进「预授权清单」，并在「终审策略声明」写明走自动终审还是强制人工终审。plan 是唯一审批工件，也是 source of truth：阶段 2 的 implementer、阶段 3 的测试 subagent 都以 plan 对应章节为唯一需求源，长内容一律写进 plan 按章节引用；批准日期与通道只记录在 plan 状态行。阶段 3 的每个 Candidate Head 均按本 plan 验证，修复后按影响面执行定向回归与计划内 regression sanity。

```markdown
# <需求名> — 实施 plan

> 状态：<待审核 / 已获批准（YYYY-MM-DD，宿主人工通道）>
> 仓库：<repo>；分支 `feature/<...>`；<push 纪律，如：不 push / 合并后 push>
> Base：`<base-hash>`

## 1. 背景与目标

<为什么做；现状是什么；做完后世界变成什么样。目标逐条编号，可验证。>

## 2. 验收标准

<终审时逐条核对的硬判据。每条可观测、可复现（命令 / 文件 / 行为），不写主观形容词。>

<定稿前逐条做承接核对：每条验收标准点名或隐含的文件 / 目录 / 语义面，都要能指到第 6 节
某个 task 的文件集，和第 9 节某个测试项的实际执行范围，三者范围同宽。验收标准使用范围词
（活动面、全库、某层全部文件）时，测试项不得收窄为若干示例文件。核对不通过就改验收标准
的范围或补 task / 测试项，不留到实施期被动暴露。>

## 3. 预裁决记录

<写 plan 前一次性批量澄清的结果，逐条记录「问题 / 推荐答案 / 用户裁决」。plan 获批后
实施期不再就已裁决项复问；无待澄清项写「无剩余待澄清项」。>

| 编号 | 问题 | 推荐答案 | 用户裁决（原文或摘要 + 日期） |
| --- | --- | --- | --- |
| Q<n> | <一句话问题> | <推荐答案 + 理由> | <裁决 + YYYY-MM-DD> |

## 4. 预授权清单

<plan 批准即一并授权、执行时不再二次确认的动作，逐条编号写清对象与边界：commit 与
合并纪律、运行态变更、收尾工件落盘、清场动作等。清单外的破坏性或不可逆动作（删除
历史工件、`--force` 类操作、未声明的远端 push）不属本清单授权范围，出现时停下报备。>

1. <动作 + 对象 + 边界>

## 5. 终审策略声明

<默认自动终审：验收标准全 PASS、零 Critical / Important、零 INCONCLUSIVE、无预授权外
待裁决项，四条件全满足即按第 4 节预授权合并；任一不满足则停下升级人工。涉及真实数据
迁移、生产环境、安全边界或其它高风险面时，改写为「本需求强制人工终审」并说明理由。
本节是合同项，实施期不得由主控自行降级。>

## 6. Task 列表

<每个 task 一个小节。task 划分以「一个 implementer 一次派发可完成」为粒度。>

### Task <X> — <名称>（<串行 / 并行组 Pn>）

- [ ] 未开始（贯穿型主控自留 task 用 `- [~] 贯穿进行中` + 子步骤逐条注记）
- **目标**：<该 task 交付什么>
- **文件集**：<显式列出允许新建 / 修改的文件路径；implementer 只准碰这些文件>
- **执行模式**：<串行 / 并行组 Pn；未完整填写并行隔离字段时必须写串行>
- **隔离位置**：<串行 task 的 feature worktree，或并行 task 的独立 worktree 绝对路径>
- **task 分支**：<串行 task 使用 feature 分支；并行 task 使用独立 task 分支>
- **集成顺序**：<串行序号；并行 task 也必须声明回 feature 分支的串行集成顺序>
- **冲突处置**：<冲突时停止的位置、由谁判断；实现冲突交独立 implementer>
- **完成判据**：<implementer 自测的逐项判据：命令 + 预期输出>

<若 task 修改流程语义，文件集必须枚举权威 SKILL、关联模板及复制该语义的活动
adapter；完成判据必须包含活动文件旧措辞 / 相反语义扫描与 source/template 逐项核对。
历史文档只列显式白名单，不批量改写。>

<去重 / 瘦身 / 合并类 task 还要做反向核对：被删除的每条约束都必须在全库有承接者。完成
判据写成「逐条列出被删约束 + 其新出处的 `rg` 命中」；全库零命中即为内容丢失而非位置
迁移，须补回或在 plan 明示放弃并说明理由。旧措辞扫描只查「该消失的是否还在」，查不出
这类丢失。>

<并行组显式标注（没有则写「无并行组，全部串行」）。同一工作树任一时刻最多一个
写入者；文件集不相交本身不构成并行授权：>

**并行组 P<n>**

| Task | 独立 worktree | task 分支 | implementer 文件集 | 串行集成顺序 | 冲突处置 |
| --- | --- | --- | --- | --- | --- |
| <i> | `<绝对路径>` | `task/<...>` | <路径枚举> | <n> | <停止点与责任人> |
| <j> | `<另一绝对路径>` | `task/<...>` | <与 task i 不相交的路径枚举> | <n+1> | <停止点与责任人> |

<并行必须同时满足：独立 worktree、独立 task 分支、implementer 文件集两两不相交、
串行集成顺序和冲突处置均已明确。任一缺失就改为串行。主控在对应 worktree 创建原子
task commit 后，才按上表顺序逐个集成到 feature 分支。>

<运维、安装、环境变更等实质工作也必须各自列为 task，由宿主派独立执行 subagent。
仅只读 sanity、范围核对、分支 / worktree 管理、精确暂存、commit、状态工件回写与呈现
审核工件可列「主控自留步骤」：逐条命令 + 预期结果 + 异常处置。每个 task 的 payload、
必要使用文档、plan checkbox 及环境绑定要求的项目路由 / 状态工件必须进入同一个原子
task commit；commit 失败须立即恢复未完成状态。无则省略。>

<声明为阶段 4 交付动作的 task（部署、服务重启、运行态冒烟等终审通过后才执行的项）
同样要收口：执行完成后由主控在其所在仓提交只含该 task 状态的 commit，写明实际结果与
证据位置；report 已冻结不改写，收口证据落在 plan 的该 task 与 knowledge。阶段 4 task
的 checkbox 不得停留在「未开始」，也不得在终审通过（自动终审四条件全满足，或强制人工
终审下取得明确批准）前预先勾选。>

<贯穿多个阶段的主控自留 task 用 `- [~] 贯穿进行中`，注记里逐条列出已完成与未完成的子
步骤，每完成一个子步骤即回写。不得因整个 task 未收口就长期停留在「未开始」——那与已发生
的子步骤矛盾，属完成性记载失真。>

## 7. 外部工具入口 dry-run sanity

<涉及第三方框架 / CLI 入口命令时，对应 task 的第一个 Step 必须是 `--help` 或最小
spike，并写明预期输出（如「输出含 usage: ...」）；确认入口存在再写依赖它的后续步骤。
不涉及则写「无外部工具入口，本节空」。>

## 8. 已知弹性点

<预判可能不按预期走的地方 + 触发时的处置（如：只记录写入 report 待裁决，不现场硬调）。>

## 9. 测试计划

<阶段 3 测试 subagent 的执行依据，逐项编号：命令 + 预期结果。覆盖：结构 / 功能 /
regression sanity，并标明代码变化后必须重跑的受影响测试，用于修复后的定向回归。先按
依赖、写冲突、共享运行态和证据文件划分测试组；明显独立、非微小且日志隔离的子项标注
为可由多个 fresh tester 并行执行，小型或共享状态测试不强制拆分。每项须指定独立证据
位置、结论口径，并要求证据记录被测 Candidate Head。账单、网络等瞬时通道错误只阻断
本项，核对现场后使用完全相同参数重试，不定性为功能失败，也不得停止其它独立项；同
参数重试不产生新 Candidate 周期，同一未变化 Candidate Head 不得无理由重复测试。
测试 subagent 发现问题只记录不修复。每个 harness 断言须指向本 plan 的验收标准或测试
项，禁止测试器临场增加验收。
每项命令写明运行 cwd（或使用不依赖 cwd 的路径）与解释器 / 运行时的确定入口：同名
可执行文件在本机存在多个版本时，必须在**每一条会执行它的 task 完成判据与测试项命令
本身**里写绝对路径（如 `/opt/homebrew/bin/python3`），或把版本断言与被测命令写进同一
条判据；只在 plan 的全局口径段声明下限不算锚定——implementer 与 tester 只读自己那一
节，读不到全局段。不把「全量全绿」口径交给执行者的 `PATH`。扫描类断言（rg / grep）先对现状
真跑一遍校准口径：预期命中数与不属于本需求消除范围的既有命中（例外白名单）逐条
写全，不留给测试 subagent 临场自行判断。
扫描 / 摘录类测试项须写明它承接哪条验收标准，且枚举的文件集与该验收标准声明的范围
同宽；范围词不得在测试项里降级为示例文件。摘录式一致性核对（逐文件摘录语句再比对）
尤其容易窄化，须把范围来源写在测试项里以便 reviewer 核对。
涉及模型 / agent 的长任务，须按任务复杂度声明观察边界并保存可核验的进度事件；不要
固化具体模型或通用固定秒数。仅出现超时或未分类 runtime error、且无明确契约违例时，
结论写 `INCONCLUSIVE`，同时附进度证据和观察边界；已有明确失败不得降格。
`INCONCLUSIVE` 不计为 PASS，必须进入 report 待裁决项；若导致计划内证据覆盖不足，
不得冻结 Final Code Head。
每个 Candidate 的测试后须由 fresh whole-branch reviewer 审查 `Base..Candidate Head`
和对应证据。tester 的 FAIL 与 reviewer 的 Critical / Important 都进入独立 implementer
修复路径；修复形成新 Candidate Head 后，至少执行受影响测试、上述 regression sanity
和必要的定向回归，再重新 whole-branch review。旧证据只有在 reviewer 证明后续变化未
影响对应代码、依赖和运行态时才可复用，并须为 report 留下证据 Head 与复用理由。
交付物对接真实外部数据（对象存储 / 线上采集 / 第三方服务）的管线类需求，测试
计划须含一次小规模真实数据端到端冒烟（~100 条真实数据，开发期不做全量）——单测
与 mock 造不出数据现实：空文件、已被生命周期清理的对象、异常长度样本、连接僵死。
实时数据源或共享缓存会漂移时，测试计划须分两层：固定业务 ID（如 utt）或版本化快照
承担严格回归；日期 / 类别 / 场景 / 实时缓存窗口只作探索性冒烟。严格 fixture 先写
存在性与可评估性预检；补充窗口不得覆盖原命令结果，须并列留证。>

## 10. 范围外（不做）

<明确不做的事，防 scope 溢出。>
```

## 使用要点

- plan commit 后直接呈现 plan；人工批准后只更新顶部状态行并 commit，不新增伴生审核工件。
- plan 批准是唯一常规人工闸门。写 plan 前把技术选型、范围与细节问题一次性批量提问（每问附推荐答案），裁决逐条写进「预裁决记录」；原需中途确认的动作提前写进「预授权清单」，获批后不再产生常规中途确认。
- 「终审策略声明」默认自动终审；高风险需求必须显式写「本需求强制人工终审」，届时须取得用户对当前 Final Code Head 的明确批准才允许合并。
- **plan 修订分类**：获批后修改 plan 分两类。**Contract change**（改验收标准、范围、安全边界、预授权清单、终审策略）必须重新取得人工批准，批准前不得按新内容执行；证据细化、状态更新与合同内实现细节由主控直接记录，不重新发审。分类不明时按 Contract change 处理。
- `docs/development/` 对每个任务只允许 `*-plan.md` 与 `*-report.md` 二件套；`closeout` 不属于任务工件，完成结果交由环境绑定的 knowledge 目录承载。
- 同一工作树任一时刻最多一个写入者。并行 task 必须各用独立 worktree / task 分支，implementer 文件集两两不相交，并预先声明串行集成顺序与冲突处置；文件集不相交本身不构成并行授权。
- agent 类型、model 与 effort 不写入 task 约束，由宿主原生 orchestrator 按任务选择；不要求子任务配置与父任务相同或不同。
- task 文件集含「新建且拟入 git」的路径时，plan 定稿前由主控逐一执行 `git check-ignore -v --no-index <path>`；命中规则则在「主控自留步骤」写明精确 `git add -f <file...>` 与 `git ls-files --error-unmatch <file...>` 核验，禁止 force-add 整个目录。
- 完成判据写成「命令 + 预期输出」，implementer 照跑即可自测，避免主观判断。
- 完成判据引用文件集 / 文件树时写「与枚举逐项对照」，不另写总数数字—— 枚举与计数并存必生笔误，以枚举为准。
- plan 获批后如需 plan 外工作：先把新 task 章节写进 plan（或转 TODO），再动手。
- implementer 不勾 task checkbox。主控只在 implementer 交还写入权、自测合格后，把 payload、必要使用文档和对应状态一起精确暂存为原子 task commit；commit 失败不得留下已完成 checkbox。并行 task 的 commit 随后按 plan 顺序串行集成。
- 流程语义 task 收口前必须核对权威 SKILL、关联模板和活动 adapter；扫描范围只含活动文件，历史文档作为显式白名单保留。
